# Projeto: itens 3.2, 3.4 e 3.6 da rede social

## Objetivo

Implementar, em Python e de maneira didática, os três itens atribuídos a Henrique no trabalho em grupo: sugestão de usuários, consulta de posts por intervalo e ranking de engajamento. O código deve usar somente listas, classes, tipos primitivos e strings; não pode usar `dict`, `set`, `heapq`, `sorted()`, `list.sort()`, `bisect` ou `collections`.

## Escopo

Incluído:

- Item 3.2: `SUGERIR @usuario k`, com grafo por lista de adjacência e heap própria.
- Item 3.4: `POSTS_ENTRE data1 data2`, com árvore AVL própria e busca por intervalo podada.
- Item 3.6: `RANKING`, com Merge Sort próprio e desempate pelo `@usuario`.
- Classes e funções com docstrings e comentários nas partes que exigem raciocínio.
- Funções públicas simples para o `main.py` ou para a integração feita pelo colega.

Não incluído:

- Itens 3.1, 3.3 e 3.5, que são responsabilidade do outro integrante.
- Bônus de API por argumentos e JSON.
- Bibliotecas externas e estruturas prontas proibidas.

## Abordagens consideradas

1. Colocar tudo em `main.py`: menos arquivos, mas torna o código grande e aumenta conflitos de edição com o colega.
2. Separar as estruturas em módulos: cada estrutura fica clara, testável e pode ser integrada no menu sem editar sua implementação.

Foi escolhida a abordagem modular por ser mais segura para o trabalho em grupo e mais fácil de explicar ao professor.

## Organização proposta

```text
py/
  grafo.py        # lista de adjacência e sugestão de usuários
  heap.py         # heap de máximo reutilizável pela sugestão
  avl.py          # nós, rotações, inserção e consulta por intervalo
  ordenacao.py    # Merge Sort e comparação de engajamento
  main.py         # carregamento e menu; integração com os outros itens
```

## Item 3.2 - Sugestão de usuários

`GrafoSeguidores` terá uma lista de listas. Como os IDs fornecidos variam de 1 a 2000, a posição `id - 1` guarda a lista dos usuários que aquele ID segue.

Fluxo:

1. Localizar o ID correspondente ao `@usuario` por uma busca linear nos usuários. Essa escolha evita depender da tabela hash que será entregue pelo colega; na integração, essa busca poderá ser substituída pela estrutura dele sem alterar o grafo.
2. Para cada usuário seguido pelo usuário de origem, percorrer quem ele segue.
3. Ignorar o próprio usuário e usuários que já são seguidos pela origem.
4. Criar vetores simples, indexados por `id - 1`, para marcar os usuários já seguidos e contar quantas conexões em comum cada candidato tem. Uma lista separada guarda somente os IDs que se tornaram candidatos. Isso substitui um dicionário, que é proibido, sem fazer buscas lineares repetidas.
5. Inserir cada candidato na heap de máximo, cuja prioridade é a quantidade de conexões em comum. Em empate, o menor `@usuario` vem primeiro, para uma saída estável e explicável.
6. Remover até `k` elementos da heap e montar a resposta.

O grafo é criado uma vez ao carregar os dados. A sugestão custa `O(U + g + c log(c + 1))`, onde `U` é a quantidade de usuários (para localizar o `@usuario` e iniciar os vetores), `g` é a quantidade de arestas percorridas a partir dos seguidos diretos e `c` é o número de candidatos distintos.

## Item 3.4 - Posts entre datas

`ArvoreAVLPosts` usa a data (`AAAA-MM-DD`) como chave. Como esse formato pode ser comparado lexicograficamente, não é necessário converter strings para objetos de data. Cada nó contém a data, uma lista simples dos posts daquela data, referências para filho esquerdo e direito e a altura.

Na inserção, a árvore atualiza alturas e aplica as quatro rotações AVL: esquerda, direita, esquerda-direita e direita-esquerda. A consulta por intervalo usa uma travessia podada:

- desce à esquerda somente se a data atual for maior que a data inicial;
- inclui a lista do nó se a chave estiver no intervalo;
- desce à direita somente se a data atual for menor que a data final.

Assim, ela não percorre ramos cujas datas estão certamente fora do intervalo. Após reunir os nós em ordem de data, os posts do mesmo dia permanecem na ordem de leitura do CSV.

Inserir um post custa `O(log d)`, em que `d` é o número de datas distintas. A consulta custa `O(log d + r)`, onde `r` é a quantidade de posts devolvidos; o acumulador usa apenas uma lista simples.

## Item 3.6 - Ranking

O ranking calcula, para cada usuário:

`engajamento = seguidores * 2 + soma_das_curtidas_dos_posts`

Os vetores auxiliares `seguidores_por_id` e `curtidas_por_id` têm tamanho 2000, sendo acessados por `id - 1`. Isso elimina a necessidade de dicionários. O Merge Sort ordena a lista de registros do maior engajamento para o menor; se houver empate, compara `@usuario` em ordem alfabética crescente.

O cálculo dos vetores custa `O(U + E + P)` e o Merge Sort custa `O(U log U)`, para `U` usuários, `E` conexões e `P` posts.

## Integração e testes

Os módulos não deverão executar código ao serem importados. O `main.py` continuará usando `aedlib.social_carregar_dados()` e construirá as três estruturas uma vez antes de mostrar o menu. Ele terá as opções `SUGERIR`, `POSTS_ENTRE` e `RANKING`: a primeira mostra até `k` recomendações, a segunda lista os posts do intervalo e sempre informa o total encontrado, e a terceira mostra os 20 primeiros colocados. Usuário inexistente, `k` não positivo ou não numérico, datas malformadas e intervalo invertido recebem mensagem clara, sem encerrar o menu.

O `RELATORIO.md` do grupo deverá documentar a contribuição dos itens 3.2, 3.4 e 3.6, as decisões acima, as complexidades e os testes realmente executados.

Casos manuais mínimos:

- usuário inexistente e `k` maior que os candidatos;
- usuário sem seguidos e usuários sem recomendações;
- intervalo com data inicial/final incluídas, sem posts e datas invertidas;
- ranking com empate artificial em teste unitário pequeno e ranking completo com 20 primeiros.
